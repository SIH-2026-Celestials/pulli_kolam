## Root cause of multiplicity = 3 (traced to exact code, not inferred)

`engine/learned_generation.py:65`  -  `DEFAULT_REPAIR_MAX_MULTIPLICITY = 3`,
one strand higher than the search phase's own `DEFAULT_MAX_MULTIPLICITY = 2`
(`engine/novel_generation.py`). The repair loop
(`engine/learned_generation.py:295-303`) doubles an edge's strand count for
every Chinese-Postman correction path that crosses it, refusing only once
the cap of 3 is hit.

**Cross-referenced against the real corpus (`structural_dataset_report.json`,
500 patterns, 181,966 measured edges): maximum observed multiplicity is 2,
in every single pattern, zero exceptions.**

→ **Classification: C  -  absent from the real training distribution.**
`DEFAULT_REPAIR_MAX_MULTIPLICITY = 3` is a code artifact with no empirical
support. It is not "rare but real" (classification B) or "an inherent
requirement of parity-closing"  -  it is one specific constant, one strand
above what real data ever exhibits, chosen without a documented reason
findable in the repository.

## What this means for the diagnosis question

The M5 generator's real bottleneck is **connectivity during search**, not
repair or multiplicity per se. Repair is not "broken"  -  it does its one job
(closing parity) essentially perfectly. The multiplicity-3 problem is a
narrow, structurally-isolated bug: one integer constant that happens to be
wrong relative to the evidence, layered on top of an otherwise-correct
mechanism. See `M5_1_CONSTRAINT_SPEC.md` for the resulting constraint
recommendation and `m5_1_counterfactual_report.json` for the measured
effect of correcting it.
