# Changelog

All notable changes to PULLI are documented here. Dates are release-candidate
dates, not calendar milestones — this project has not yet had a numbered public
release.

## [Unreleased] — Production Candidate

Full frontend/backend integration, M4.2 recognizer verification, M5 generation,
mathematical/graph/symmetry/complexity/novelty analysis, generation persistence
and history, SVG/PNG export, PostgreSQL support with real-Postgres verification,
generation ownership/authorization, rate limiting, security headers, Docker
hardening, and a verified backup/restore procedure. External cloud staging/
production deployment (Vercel/Render/Supabase/R2) has **not** happened — it is
explicitly reported as pending, not claimed as done.

### Added
- Generation ownership / authorization: every generation is now private to the
  account that created it. `GenerationRequest.user_id` (Alembic migration),
  auth required on every generation route, ownership-checked retrieval
  (`GET`/`DELETE`/`/mathematics`/`/graph`/`/export`) — a request for another
  user's generation returns the same 404 a nonexistent id would.
- Artifact deletion: `DELETE /api/v1/generations/{id}` removes the DB rows and
  the underlying storage object together, with a documented safety ordering
  (DB commit first, storage cleanup best-effort after).
- Security headers middleware (`api/security_headers.py`): HSTS,
  `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`,
  `X-Frame-Options`, and a `Content-Security-Policy` (relaxed only for
  `/docs`/`/redoc`, strict everywhere else).
- Per-user rate-limit isolation for the generation endpoint (previously
  IP-only, so different logged-in users behind the same IP shared one quota).
- `docs/DISASTER_RECOVERY.md`, including a real, executed backup/destroy/
  restore/verify drill against disposable PostgreSQL (15 steps, all passing).
- `api/tests/test_rate_limit.py`, `api/tests/test_security_headers.py`, and 11
  new ownership/deletion regression tests in `api/tests/test_platform_generations.py`.

### Fixed
- **CORS**: `allow_methods` was missing `DELETE`, which would have silently
  broken artifact deletion from any real cross-origin browser (the actual
  Vercel-frontend-to-Render-backend production topology).
- **PostgreSQL — index overflow**: `pattern_versions.fingerprint` was indexed,
  but a large pattern's fingerprint exceeds Postgres's btree index row-size
  limit; the index was dropped (confirmed unused by any query first).
- **PostgreSQL — integer overflow**: `generation_results.seed` was a 32-bit
  `Integer`; random seeds up to 2³²-1 overflowed it on Postgres (silently
  tolerated by SQLite). Widened to `BigInteger`.
- **Alembic migration bug**: the autogenerated fix for the seed-overflow issue
  used a bare `ALTER TABLE ... ALTER COLUMN`, invalid SQLite syntax that would
  have broken the next migration run against a fresh dev database. Fixed with
  `op.batch_alter_table`.
- **Docker packaging**: the production image never included the dataset CSVs
  (`kolam19.csv`, `kolam29.csv`) that M5 generation loads at runtime, so a
  container built exactly per the documented `Dockerfile` would start, pass
  liveness, and be permanently un-ready. Fixed with two minimal, curated
  `COPY` lines and a matching `.dockerignore` exception.
- **Ownership type mismatch**: `User.id` (`Integer`) vs. the new
  `GenerationRequest.user_id` (`String`) round-tripped inconsistently in
  SQLite, meaning even the correct owner could get a 404 on their own
  generation. Fixed by stringifying consistently at every write/compare site
  — caught by the new regression tests failing, not by inspection.

### Verified (real infrastructure, not inspection)
- Full Alembic migration chain, upgrade and downgrade, against a real,
  disposable PostgreSQL 16 instance (Docker).
- `api/tests/` (94 tests) passing against both local SQLite and real Postgres.
- A real `docker build` + `docker run` of the production image, including a
  live check that the container runs as a non-root user and a complete
  real generation executed through it end-to-end.
- Concurrent-load benchmarking at 1/3/5/10 simultaneous requests against both
  SQLite and Postgres — Postgres produced zero request failures at
  concurrency 10 where SQLite produced two (`database is locked`).
- Security headers and the CORS fix, via real HTTP requests against a live
  server (not just code inspection).
